## 二、本轮新发现的、此前未注意到的事实

**`compatibility=0` 与 `Build=FAILED` 可以同时出现。**

u1_cos / u2_sin / u4_less / u5_and / u7_expand 五个探针都是：
```
compatibility=0
Build=FAILED
compatibility_after=0
```

**含义**：`compatibility` 与 `Build` 是**两个相互独立的检查**。
`compatibility=0` **既不能证明模型能编译，更不能证明算子在 NPU 上执行。**

这补上了此前的认知缺口 —— 我们之前只知道"fallback 会让 compatibility=0 变成假通过"，
现在知道**即使在严格关闭 fallback 的情况下，compatibility=0 也仍然不等于可编译**。

**判据必须同时满足三条**：
1. `compatibility=0`
2. `Build=SUCCESS`
3. `RunSync=SUCCESS` 且 **输出与 ONNX ReferenceEvaluator 的 oracle 数值对账通过**

## 三、对结论的影响

本次复核把"Qwen 为什么上不了 NPU"的结论从**单来源**（设备日志）加固为**双来源交叉验证**：

- 设备编译器报出缺失算子：`CastT`、`GatherV2D`、`Reshape`、`LogicalAnd`、`BroadcastTo`、`Select`、`Cos`、`Sin`、`ExpandDims`，以及 `dimCnt >= 4` 限制
- 我的独立探针确认其中可单独构造的 6 项（Cos / Sin / Less / And / Expand / Where）**确实失败**
- 而日志未点名的算子（Neg / Flatten / Sigmoid / Softmax / Slice）**确实成功**

**结论不变且更可信**：在本机可获得的工具链与公开通路范围内，
**LLM 图无法在 Kirin 9010 的 NPU 上编译执行**，原因是设备编译器逐条报出的基础算子缺失，
而非某一处写法不当。
