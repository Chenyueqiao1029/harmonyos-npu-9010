## 发现

我们的 HiAI DDK **缺少平台插件**。

证据链：

1. `<workdir>\ddk\DDK-tools-next-6.1.1.0\tools\platform\` 目录里**只有一个 README.md**，是空的。
2. 该 README 原文（逐字）：

   ```
   # 下载的插件 拷贝到当前目录

   路径如下:

   tools

   ├── platform

   │   ├── kirin9020

   │   ├── kirinx90

   ├── tools_ascendc

   ├── tools_dopt

   ├── tools_omg
   ```

   并给出 `kirin9020` 插件的完整结构：

   ```
   platform/kirin9020/
   ├── cmake/kirin9020.cmake
   ├── config/kirin9020.ini
   ├── config/kirin9020.json
   ├── lib64/libcustom_op.so
   ├── ops/impl/ascendc/activation/ascend_activation.cpp
   ├── ops/impl/custom/add_custom.cpp / add_custom.py / op_proto.h
   ├── ops/impl/impl/util/platform_adapter.py

       ├── libc_secshared.so
       ├── libmodelv310_itf.so
       ├── libmodel_v310.so
       └── model/
   ```

3. 核对 zip 全部 **2937 个条目**：**没有任何 kirin9020 / kirinx90 插件文件**，
   `tools/platform/` 下只有 `README.md`。→ 插件是**单独下载**的。

## 为什么这可能重要

`omg` 每次运行都报：

```
W/AI_FMK: parser_factory.cpp LoadCustomOpLib(59): "dlerror: libcustom_op.so: cannot open shared object file: No such file or directory"
W/AI_FMK: ops_kernel_store_manager.cpp DlopenComputeLibrary(41): "dlopen so failed: libai_npucore_itf.so: ..."
```

**我们是在没有目标平台算子定义与算子实现的情况下做的转换。**

`config/kirin9020.json` 很可能就是该平台的**算子支持清单**；`ops/impl/` 是**算子实现**；
`libcustom_op.so` 正是 `omg` 报缺的那个库。

## 待验证的假设（按顺序）

1. **同一份 ONNX，有/无平台插件，`omg` 产物是否不同？**
   → 用已有探针即可对照：`models/ops/r1_mul_bcast.onnx`、`r3_div_tensor.onnx`、`r4_mul_flat.onnx`
   → 比对 `.om` 的字节数与真机 `compatibility`
2. **带插件转换出的 Qwen `.om`，真机 `compatibility` 会不会变成 0？**
3. **平台列表里只有 kirin9020 与 kirinx90，没有 9010** —— 这是否本身就是结论？
   如果 9010 不在官方平台列表内，那"大模型上 NPU"这条路大概率不通，
   应据此给出止损结论，而不是继续试。

## 风险与反面可能

- **反面可能 A**：平台插件只影响**自定义算子**（AscendC 写的），与标准 ONNX 算子的
  支持与否无关 —— 那我们那批探针的结论不受影响。
- **反面可能 B**：插件的 `config/*.json` 只是**编译期算子实现**，而设备侧
  `compatibility` 判定用的是**设备自己的**算子表 —— 那装插件也改不了 `compatibility=1`。
- 因此**必须做对照实验**，不能因为"缺东西"就假定"装了就好"。
