## 一、已经确证的（真机实测，有原始日志）

### 1.1 HiAI Foundation 通路可用

| 项 | 证据 |
|---|---|
| 官方 SqueezeNet `.om` | `compatibility=0`，`Build=SUCCESS 30ms`，`RunSync=SUCCESS 2ms`，输出 1000 类 softmax `sum≈0.998` `NON_ZERO`；CPU 序对照 `RunSync=10ms` |
| 我们自产的 `tiny_conv.om`（1462 B，`omg` 生成） | `Build=SUCCESS 9ms`，`RunSync=SUCCESS 1ms`，输出非零合理 |
| 小注意力图 `p6_tblock` | `compatibility=0`，`Build=SUCCESS 10ms`，非零输出 |

→ **NPU 不是摆设，普通张量乘法、动态除法、若干广播、小注意力图都能严格 NPU Build/Run。**

### 1.2 Qwen2.5-0.5B `.om` 被判定不兼容

- 产物：`qwen_s8.om`，1,027,575,060 B，魔数 `IMOD`，`omg` exit 0
- 真机：`model_bytes` 读全，**`compatibility=1`**（`HIAI_COMPATIBILITY_INCOMPATIBLE`），`Build=FAILED 121ms`

### 1.3 根因清单（来自设备自己的编译日志）

用户既有完整 Qwen 真机日志逐条报出：

```
CastT datatype not support
GatherV2D ... not supported
LogicalAnd ... not supported
Select ... not supported            <- ONNX Where
Cos ... not supported               <- RoPE
Sin ... not supported               <- RoPE
expanddims_check_support.cc CheckExpandDimsSupport(40):: not support input dimCnt >= 4!
BroadcastTo ... not supported
```

**注意限定**：这些行针对**某个 NPU 算子库**，不能直接扩大为"所有库、所有 dtype 一律不支持"。
但它足以**否定**"只把 Div 换掉就能让整图兼容"这类推断。

**`dimCnt >= 4` 这一条影响最大**：transformer 的注意力张量天生 `[B,H,S,D]` 四维。

## 二、方法论上的重大更正（codex 查出，我此前结论受其影响）

**`compatibility=0` 在有 fallback 时不能证明算子在 NPU 上执行。**

- `hiai_options.h` 写 `HIAI_FALLBACK_ENABLED = 0` 为默认值，但运行时日志出现 `fallBackMode: 1`
- 旧 `r1` 在 fallback 开启时 `compatibility=0`；**关闭 fallback 后 `Build FAILED`**，日志：
  ```
  CheckSupported: the op name [y] type [Mul] is not supported in npucl store [elementary_lib]
  CheckSupported: the op name [y] type [Mul] is not supported in npucl store [fe_lib]
  deviceType: 0, fallBackMode: 1
  op y device type 0 is not supported in chkResult
  general_model_compiler.cpp BeforeCompile(172)::check ir model compatibility failed
  ```

→ **我此前"r1 兼容、r4 不兼容"的整批归因不可靠**，必须一律在**显式关闭 fallback** 下重测。

### 另外两个我自己犯的混杂

1. `build_rcorrection.py` 里 `n=Sqrt(v)` 实际形状是 `(4,1)`，所以 `r4` 的 `(4,8)` 仍需广播 ——
   **`r1` 与 `r4` 根本不是"广播 vs 不广播"的对照**，我读错了自己的实验。
2. `q1`、`q4`、`r3` 把实际 `(4,1)` 的输出声明成 `(4,8)`，`full_check=True` 会直接报
   `Inferred shape and existing shape differ in dimension 1: (1) vs (8)`。

### 还有一条：数值验证不能只看"非零"

负轴归一化链 + 动态 Div 的探针：`compatibility=0 / Build SUCCESS / RunSync SUCCESS`，
**但非零输入得到全零输出，oracle MISMATCH**。
→ **Build/Run 成功 ≠ 数学语义正确。必须有 oracle 数值对账。**

## 四、MiniCPM-V 4.7 线的结论

**官方鸿蒙部署路线只走 CPU，没有 Kirin NPU 后端**（依据：实际 HAP 的 ELF 依赖与源码配置）。

- **1B**：SHA256 已验证，独立测试 HAP 已编译；**真机未跑通**（官方包被 UDID 签名授权拒绝，随后 USB 通信失败）
- **35B-A3B**：完整分片 **16.624 GB**；鸿蒙端还缺 LES 参数接线与实测；闪存速度与稳定内存均未验证 → **建议暂缓业务替换**
- **替换现有 Qwen（端侧 CPU 路线）**：中等改造，需统一重编 NAPI / llama.cpp；**直接换 `.so` 有 ABI 冲突风险**

→ **对"NPU 打通"目标无直接帮助；对"端侧多模态替换"是可行候选。**

## 五、架构层面的旁证

- 华为官方 CANN LM Engine 文档：**硬件要求 Kirin X90 平台**；支持模型列表含 Qwen2.5-1.5B / Qwen2.5-7B / Qwen3-8B / Glm-1.5b
- 本机 `canIUse("SystemCapability.AI.CANN.LLMEngine")` 返回 **false**
- 官方平台插件只有 **kirin9020 / kirinx90 / kirin9030**，**没有 9010**
- 华为合作伙伴做 GLM-Edge-1.5b 时，**RmsNorm 是手写 Ascend C 自定义算子**实现的

**可下的结论**：本机**不具备该公开的 LLM 专用通路（LM Engine）**。
**不能**由此外推"HiAI Foundation 发现 LLM 结构就一律拒绝执行" —— 真机数据已证明它能在 NPU 上严格执行多种算子。

## 六、当前阻塞（唯一）

- 现象：先 `[Fail][E000004] The communication channel is being established`，反复 `hdc kill`/`start` 无效；
  随后变成 `[Fail][E001005] Device not found or connected`
- 已尝试：`hdc kill` + `hdc start`（三次）、`power-shell wakeup`（`WakeupDevice is called`，但 `setmode` 失败，当前 mode 601）
- **需要用户配合**：解锁手机屏幕并重新插拔 USB

**这不是硬件理论不可能，是临时连接问题——不能写成止损结论。**
